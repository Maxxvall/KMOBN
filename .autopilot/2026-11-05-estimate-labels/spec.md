# Спецификация: метки смет и источники расчёта дома

## Задача

Пользователь сам выделяет просчитанные типовые проекты и другие группы смет. В текущих сметах он выбирает несколько меток и получает только сметы, содержащие все выбранные метки. Расчёт дома опирается исключительно на вручную отмеченные типовые проекты.

## Решение

### 1. Справочник меток

- Начальный справочник содержит постоянную системную метку «Типовые проекты». Она не переименовывается и не удаляется: это стабильный признак источника калькулятора.
- В раскрывающемся списке есть «Добавить метку». Пользовательские метки можно добавлять, переименовывать и удалять. Кнопки доступны мышью, клавиатурой и на сенсорном экране, без зависимости от hover.
- Название обрезается по краям; пустые названия и дубликаты без учёта регистра/лишних пробелов отклоняются с понятной ошибкой. Конечная длина ограничивается разумным пределом (64 символа), без усечения введённого значения молча.
- Переименование меняет единую запись со стабильным ID: новое имя сразу видно в текущих, архивных, открытой смете и её версиях. Количества и суммы смет не меняются.
- Перед удалением пользовательской метки показывается подтверждение, что метка будет снята со смет. Сами сметы сохраняются. Удалённая метка не появляется снова при открытии старой версии или повторном сохранении старого черновика.
- Справочник использует существующее хранение по пользователю/workspace, offline-очередь и облачную синхронизацию. Ошибка сохранения видна пользователю; прежние подтверждённые данные сохраняются. Смена аккаунта не переносит его метки другому пользователю.

### 2. Метки в редакторе

- Рядом с полями клиента, типа строения и площади появляется подписанное поле «Метки» с множественным выбором.
- Можно назначить ноль, одну или две разные активные метки. При двух выбранных остальные варианты недоступны, пока одна не снята. Пользователь видит выбранные названия и ограничение «До 2 меток».
- Старые сметы открываются с пустым выбором. Ни название клиента, ни тип строения, ни статус не назначают метки автоматически. Пользователь вручную отмечает типовые проекты.
- Назначение метки считается изменением сметы: работает существующий индикатор/защита несохранённых изменений, обычное сохранение и повторное открытие. Повторное сохранение неизменного значения не создаёт лишней offline-операции.
- Новая версия той же сметы сохраняет метки. Отдельная копия сметы и новый черновик из расчёта дома создаются без меток. Создание обычной новой сметы также начинается без меток.
- Удаление метки из справочника освобождает слот в редакторе, включая открытый черновик, и не может вернуть удалённую метку последующим Save.

### 3. Фильтр текущих смет

- Рядом с «Текущие» и «Архив» расположен раскрывающийся список «Метки»; он применяется и доступен только в «Текущих». Архив показывает свой обычный набор независимо от выбранного фильтра.
- Можно выбрать несколько меток; их чекбоксы и выбранные названия видны в списке. Пустой выбор означает «Все метки». Есть способ показать «Без метки» и сбросить выбор; этот режим взаимоисключается с конкретными метками.
- Совпадение — AND. Для выбора «Типовые проекты» + «Баня» подходит только смета, содержащая обе. Смета только с «Типовые проекты» не подходит. Для выбора одной метки подходит смета с ней и любая её вторая метка.
- Фильтр пересекается с уже существующими поиском, клиентом и другими фильтрами текущей истории. Существующая сортировка и принцип отображения последних версий не меняются.
- Назначенные активные метки читаются рядом с данными сметы в списке, чтобы результат фильтра был понятен. Удалённая из справочника метка исчезает из выбранного фильтра и отображения.
- Нет совпадений — понятное пустое состояние с возможностью сбросить фильтр.

### 4. Расчёт дома

- Во всех путях подбора исходных цен и аналогов обязательна системная метка «Типовые проекты»: основной алгоритм, дополнительные позиции, резервный подбор, AI-первичный запрос и повторная AI-проверка, включая обновлённые данные после refresh.
- Статус «Черновик», «Отправлена» или «Согласована» и давность сметы не ограничивают вручную отмеченный типовой проект. Проверки пригодности данных остаются: неархивная смета, положительная площадь и позиции для расчёта. При нескольких версиях одного типового проекта не использовать устаревшие версии вместо актуальной.
- Обычная смета без этой метки никогда не становится запасным источником. Название, клиент, внутреннее пояснение и близость площади не обходят ограничение.
- Если пригодных типовых проектов нет, расчёт и AI не переходят к обычным сметам; выводится предложение добавить/отметить сметы с меткой «Типовые проекты».
- Подсказки и объяснение источников соответствуют новой логике, без прежних обещаний о всех согласованных сметах/свежих черновиках.
- Остальные формулы, комплектации, наценки, геометрия и форматы выдачи сохраняются. Ретроспективная статистика точности не является источником цен и меняется только если её данные попадают в ценовой/AI расчёт.

### 5. Совместимость и перенос

- Поле назначения меток необязательно; отсутствие в старой записи эквивалентно пустому массиву. Внешние значения валидируются на границе: строковые уникальные ID, не более двух активных меток, без приведения повреждённых данных через unsafe casts.
- Справочник расширяет существующий JSON-документ настроек разделов. Его нормализация, базовый snapshot, three-way merge и разрешение offline-конфликтов сохраняют определения меток и удаления, не уничтожая существующие определения/порядок разделов.
- JSON backup/restore сохраняет назначение вместе с необходимыми определениями для распознавания ID после импорта, в том числе при экспорте только смет. Переиспользуются существующие конверты/snapshot и flow; не вводится отдельный формат хранения. Импорт старых файлов без меток совместим. Удалённая метка не возрождается из старого snapshot при возврате в тот же справочник. Импорт переданной отдельной сметы как нового объекта считается отдельной копией и очищает назначения; частный справочник меток в такую копию не переносится.
- Не менять PDF/DOCX/XLSX-раскладку ради меток: пользователь не просил печатать их. Существующие документы и экспорт сохраняют расчётные данные и порядок разделов.

### 6. Передача результата

- Дополнение пользователя от 2026-11-05 явно разрешает push на GitHub после завершения, проверок и ревью. Координатор выполняет обычный push без force, сохраняет чужую работу и сообщает коротко, простыми словами, что сделано и что проверено.
- Это завершающий операционный шаг текущего таска, без нового продуктового slice или повторного полного прогона неизменного кода.
- Позднейшее решение пользователя после сетевой ошибки: «Пока оставить результат локально». Оно заменяет push на локальную передачу: сохранить коммиты, установщик и краткий отчёт. Отправка на GitHub отложена до отдельного продолжения после восстановления связи; дальше сеть не перенастраивать и попытки не повторять.
- Ещё позднее пользователь возобновил отправку: «Интернет попался повтори». Это отменяет временную остановку. Сеть восстановлена; для обычного git выбран существующий аккаунт Maxxvall из двух сохранённых. Code 2848de5 принят origin/main; документация отправляется завершающим обычным push.

### 7. Дополнение: офлайн и ПК-версия

- Пользователь отдельно подтвердил приоритет офлайн-работы. Приёмка проверяет локальное создание/переименование/удаление меток, назначение и повторное открытие сметы без сети, queued операции и обработку base/merge/tombstones при синхронизации. Реальные пользовательские данные не используются.
- ПК-версия поднимается с текущей 1.9.0 до 1.9.1 в package metadata и lockfile. Это решение координатора для следующего patch-релиза, номер пользователь не задавал.
- После завершённых code fixes собирается установщик Windows текущими командами проекта. Build — явный release gate для нового требования; использовать publish never. Файл проверяется по наличию, версии и хешу. Не устанавливать его поверх приложения пользователя и не запускать интерактивный установщик автоматически.
- Обычный GitHub push содержит также повышение версии. Создание GitHub Release, тега с автопубликацией и загрузка бинарника на внешний сервис не запрошены и не выполняются автоматически.

## Решения по реализации

- Существующие React 19 + TypeScript + Tailwind, установленные иконки, текущие компоненты и визуальные токены. Новые зависимости не нужны.
- Подход: единый справочник со стабильными ID в существующем per-user JSONB-документе `estimate_sections`, назначения в `Estimate.labelIds`. Это даёт глобальное переименование без переписывания всех смет и без новой таблицы/миграции.
- Хранение имён независимо в каждой смете отвергнуто: массовое переименование/офлайн-синхронизация расходились бы. Отдельная таблица отвергнута: уже есть подходящие защищённые JSONB и offline-контракты.
- Удаление определяется в едином справочнике, при необходимости с tombstone. Эффективные активные ID используются в UI, лимите и фильтре; старые сохранённые ID не возвращают удалённые метки.
- Системный ID одинаков везде и никогда не вычисляется из отображаемого названия. Точные границы — `interfaces.md`.
- Проверки: адресные тесты значимого поведения, затем `npm run check` как текущий CI. Не запускать повторно полный набор на неизменном коде только ради окончания этапа.

## Вне рамок

- Остатки прошлой работы: пользователь прямо отказался включать их.
- Автоматическая разметка старых смет, более двух назначенных меток на смету, фильтр меток архива.
- Изменение формул, прав доступа, live-базы/схемы Supabase и внешняя публикация релиза. Обычный GitHub push, повышение ПК-версии и локальная сборка установщика разрешены последующими дополнениями пользователя.
- Новый дизайн приложения и добавление меток в печатные документы.
- Временная остановка push (G14) отменена пользователем «Интернет попался повтори»; действующее завершение — push и короткий отчёт (G11/G15).
