# Спецификация: Стоимость м² по комплектациям (аналитика SMETA KM)

## Задача

Владелец SMETA KM ведёт типовые проекты с меткой «Типовые проекты» и хочет знать, сколько реально стоит квадратный метр у его компании: в тёплом контуре, в подготовке под чистовую, под ключ. Сейчас в «Аналитике» есть только средняя цена за м² без разбора по комплектациям, без медианы и без понимания, какие сметы вообще можно считать. Данные о комплектации разбросаны: где-то она в расчёте дома, где-то — фразой в «Пояснении», где-то её нет вовсе. Нужен ориентир, которому можно доверять, и список смет, которые в этот ориентир пока не попали и почему.

## Решение

В разделе «Аналитика» (режим «Обзор») появляется компактный блок «Стоимость м² по комплектациям»: пять карточек — «Коробка», «Тёплый контур», «Подготовка под чистовую», «Под ключ», «Под ключ с инженерией» (фактические комплектации кода, брифинг 15.11). В карточке — ориентир за м² (медиана), диапазон мин–макс, количество проектов и обычное среднее отдельной строкой; одна смета подписывается «1 проект», пустая карточка — «Нет данных». Под блоком — строка «Ориентиры по вашим сметам, не гарантированная цена строительства».

Блок считается только по последним версиям неархивных смет с меткой «Типовые проекты» (`system:typical-projects`), у которых заполнены площадь (> 0) и итог (> 0), и только по сметам с определённой комплектацией. Группы никогда не смешивают: тип объекта выбирается фильтром (Дома / Бани / Хозблоки / Прочее, по умолчанию «Дома»), разные базы площади попадают в разные группы (площадь дома с дополнениями и без), цена для клиента и себестоимость показываются двумя раздельными строками метрик.

Комплектация сметы определяется по ступеням: сохранённое подтверждение пользователя → пакет из снапшота расчёта дома (`houseCalculationSnapshots[].input.package`, статус «из расчёта») → одна однозначная фраза в типе строения/«Пояснении» (статус «предложено», в расчёт НЕ попадает) → несколько вариантов, отрицание («под ключ без инженерии») или ничего — смета уходит в список «Требуют проверки». Подтверждение или исправление пользователь делает прямо в блоке (список проверки и строки дриллдауна); выбор сохраняется в новых необязательных полях самой сметы и больше никогда не перезаписывается автораспознаванием. Цены, площади и позиции смет блок не меняет никогда.

Рядом с карточками — панель «Требуют проверки»: сметы без площади/итога (кнопка «Открыть смету»), сметы с предложенной комплектацией (кнопка «Подтвердить» + выпадающий список «исправить»), сметы с неоднозначным распознаванием (причина словами, ручной выбор), дома со снапшотом и дополнениями (терраса и пр.) без подтверждённой базы площади («без дополнений» / «с дополнениями»). Дриллдаун по карточке — список проектов, из которых собрана цифра: номер+клиент, площадь и её база, итог, цена за м², дата, статус комплектации; в строке — компактный селектор для исправления.

Фильтры блока: тип объекта (сегментированный), регион (из данных смет + «Без региона» + «Все»), площадь (мин–макс, м²), период — общий фильтр периода страницы (пресеты + «Произвольный период», как на всей «Аналитике»). На компьютере карточки в строку, на телефоне — стопкой, фильтры переносятся.

| 4 | R04 | Тип объекта определяется из `buildingType`: «бан» → Бани, «хозблок» → Хозблоки, «дом»/«коттедж» → Дома, остальное → Прочее; блок считает только выбранный тип | карточки не смешивают дома и бани при любом фильтре |

| 8 | R08 | Если снапшота нет — комплектация ищется фразами в «Типе строения» и «Пояснении»: «тёплый контур», «под ключ», «оптимальный», «черновая», «коробка», «премиум» и похожие (общий справочник матчеров с парсером). Поля «название» у сметы в системе нет — его роль играют «Тип строения» (виден в списке смет) и «Пояснение»; фраза «каркас» комплектацией не считается (в системе это технология, а не комплектация — предложить пакет по ней значило бы угадывать, R10) | фраза «дом под ключ» даёт предложение «Под ключ»; «каркасный дом» без других фраз — статус «не определена», без ложных предложений |
| 9 | R09 | Предложенная комплектация не считается автоматически: в «Требуют проверки» видна плашка «предложено: X», кнопка «Подтвердить» и селектор исправления; подтверждение записывается в смету | после «Подтвердить» смета появляется в карточке, статус «подтверждено» |

## Решения по реализации

- **Новое поле сметы — без SQL-миграции.** Сметы хранятся как schemaless `payload jsonb` (RPC `save_offline_record`), объект уходит целиком без whitelist. В `types.ts` — `HousePackageId` (инлайн-юнион, как `HouseCalculationSnapshot.input.package` — избегаем цикла типов), `EstimateSqmAreaBase = 'house' | 'house-with-additions'`, поля `Estimate.sqmPackage?`, `sqmAreaBase?`, `sqmConfirmedAt?`. Обязательные точки: `estimateEditorSignature.ts` (dirty-детект) и `clientEstimate.ts` (`InternalEstimateField` — служебные поля не уходят в клиентские экспорты).
- **Единый справочник ключевых слов.** Матчеры комплектации выносятся из `parseHouseDescription` в экспортируемый `HOUSE_PACKAGE_MATCHERS` в `services/houseCalculator.ts`; сам парсер работает как раньше (тесты зелёные). Обёртка распознавания в новом сервисе — без копии ключевых слов.
- **Новый сервис `services/sqmAnalytics.ts`** (чистые функции, 2 пробела): `detectSqmObjectType`, `classifySqmCompletion` (ступени R07→R08→R10 с отрицаниями), `buildSqmAnalytics(estimates, filters)` → `{ groups, needsCheck, regions }`; медиана/диапазон/среднее/склонение внутри. Себестоимость — из верифицированных actual-позиций (`calculateActualItemTotal`, `actual.source === 'verified'`, только при `houseActualBasis='cost'`).
- **Новый компонент `components/analytics/SqmByPackageSection.tsx`** — весь UI блока; `Analytics.tsx` только монтирует его в режиме «Обзор» и передаёт `estimates`, колбэки сохранения и открытия сметы. Монолит не растёт.
- **Сохранение подтверждений** — патчем только новых полей через колбэк App (`onUpdateSqmFields`), который идёт обычным путём `saveEstimates` (outbox-first). Аналитика сама ничего не сохраняет.
- **Дриллдаун и панель проверки** — компактные inline-панели с ограниченной высотой и прокруткой; если список станет виртуализированным — строка только на уровне модуля (прецедент `AnalyticsItemsRow`).
- **Словарь**: «комплектация» (HousePackage), «база площади» — добавить в `CONTEXT.md`; избегать «категория»/«тег».

## Вне рамок

| Требование | Почему не сейчас |
|---|---|
| Селектор комплектации/базы площади в редакторе смет (EstimateMetaFields) | «Редактор смет — без перестройки принятого редизайна» (Договорились); подтверждение живёт в аналитике, R09 закрыт там же |
| Поле «Регион» в форме редактора смет | Регион уже есть в данных (задаётся при AI-генерации); массовый ввод регионов — отдельная работа, в этой сборке регион только фильтр |
| Переименование существующего KPI «Средняя маржа» | R15 ограничивает новый блок; существующие блоки Аналитики не трогаем |
| Экспорт блока в XLSX/PDF | не заказан |

## Открытые места

Плейсхолдеров нет: все факты пользователя либо есть в системе (метка, площадь, итог, регион), либо вводятся пользователем в новом UI. Регион у старых смет чаще пуст — фильтр показывает «Без региона», это не ошибка.

## Данные в старых сметах (R29, по notes.md)

- Есть всегда: `estimateNumber`, `total`, `area` (может быть 0/NaN — фильтровать `Number.isFinite`), `buildingType`, `labelIds`, `explanation?`, `region?` (чаще пуст), `houseCalculationSnapshots?` (только у смет из калькулятора дома).
- Комплектация явно указана только в снапшотах (`input.package`); в тексте — фразами; отрицаний парсер не знает.
- Себестоимость — только у смет с верифицированным фактом (`houseExecutionStatus='actual-verified'`, `actual.source='verified'` на позициях) и объявленной базой `houseActualBasis='cost'`.
- Подтверждённые данные храним в самой смете: schemaless payload, без миграции, офлайн-синк бесплатно; старые сборки клиентов поле молча не трогают (читают только свои поля).
