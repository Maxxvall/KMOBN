## 2. Общий вывод о качестве кода и архитектуры

Это **два разных проекта в одном репозитории**.

**Сервисный слой — заметно выше среднего.** Ядро offline-синка спроектировано по-взрослому: outbox-первым (очередь пишется до кэша), идемпотентность на сервере через `operation_id`, трёхстороннее слияние для разделов смет, push-then-pull с отказом от pull при неотправленных изменениях, карантин нераспознанных элементов очереди вместо молчаливого удаления, snapshot-проверки подтверждений. Расчётные модули (`estimateActuals`, `estimateSections`, `cutting/importCsv`, `houseCalculationSnapshot`) — чистые функции, покрытые тестами, с версионированными снапшотами. 291 тест зелёный за 4 секунды. Этого мало кто ждёт от проекта такого размера — и это есть.

**Но на стыках слоёв и в UI-файлах-гигантах качество проседает резко.** Четыре файла-монолита (App 2409, EstimateEditor 2486, Analytics 2088, openRouterService 1806 строк) держат на себе основные сценарии, и именно там сосредоточены баги: подтверждение синка заменяет весь список в UI одной записью; каждая синхронизация заново загоняет все сметы в очередь из-за расхождения форм хэширования; редактор на каждое нажатие клавиши делает O(N×M) сканы каталога. Бизнес-правила («похожая смета», статус подписки, нормализация русского текста, коэффициент кровли) продублированы по 3–7 раз с уже разъехавшимися значениями. Монетизация фактически отключена (все тарифы безлимитные), а UI при этом продаёт лимиты. TypeScript компилируется без `strict`, линт не покрывает api/electron, а два файла PDF-генераторов отключают проверку типов целиком.

Итог: **проект работоспособный и местами добротный, но его главные пользовательские и денежные пути держатся на хрупких стыках**, которые уже дают реальные баги. Хорошая новость: большинство критичных находок чинится малой кровью, без переделки архитектуры — фундамент для этого есть.

### Проблема 1. Подтверждение офлайн-синка схлопывает список данных в UI одной записью

**Приоритет:** P0

**Где обнаружена:** `services/offlineSync.ts:180-186` и `:205-209`; `App.tsx:374-410` (`handleCacheUpdate`)

**Что не так:** После успешной отправки офлайн-изменения `runQueue` диспатчит событие `kmobn:cache-update`, положив в `detail.data` **массив из одной записи** (`data: [result.confirmedRecord.data]`). Обработчик в App.tsx по контракту получает **полный** список таблицы и заменяет им состояние целиком: `setter(detail.data)` для materials/works/bundles/templates и `setEstimates(normalized)` для estimates.

**Чем это плохо:** Реальный видимый сбой данных. Сценарий: пользователь офлайн добавил материал → reconnect → синк подтверждает одну запись → список материалов в UI схлопывается до 1 записи. То же для смет. Восстановление — только по глобальному `workspaceVersion` (который `runPendingSync` не поднимает) или перезапуск. Пользователь уверен, что данные пропали.

**Доказательства:** Проверено чтением кода: `offlineSync.ts:183` — `data: [result.confirmedRecord.data]`; `App.tsx:406` — `setter(detail.data)`; `App.tsx:380-382` — `setEstimates(normalized)` от `detail.data`. Хэш-защита на `App.tsx:376` не спасает: хэш одной записи ≠ хэшу полного списка. В `services/database.ts` есть корректный хелпер `dispatchCacheUpdate`, всегда передающий полный список, — в offlineSync 5 инлайн-копий его обходят.

**Как исправить:** Слать подтверждения через один аккумулирующий канал: либо диспатчить из offlineSync через тот же `dispatchCacheUpdate` (перечитав список из кэша), либо ввести отдельный тип события `record-confirmed`, который App мержит точечно (upsert одной записи в текущий стейт), вместо замены списка.

**Эффект:** Устранение видимой потери данных после каждого офлайн-цикла.

**Риск изменения:** низкий (локальная правка канала событий, покрыть unit-тестом на merge).

### Проблема 2. Hash-churn: после каждого синка все сметы заново загоняются в очередь → лишние ревизии → PT409-конфликты на других устройствах

**Приоритет:** P1

**Где обнаружена:** `services/estimateLifecycle.ts:43-47`; `services/hashing.ts:1-12`; `services/supabase.ts:175-186`; `services/database.ts:478-481`

**Что не так:** `normalizeEstimateChains` создаёт у каждой сметы явный ключ `parentId` со значением `undefined` (`normalized.push({ ...item, parentId })`). Собственный `stableStringify` проекта строится на `Object.entries` и **включает** ключ со значением `undefined` в строку хэша, а `JSON.stringify` (которым запись уходит в Supabase JSONB) ключ **выбрасывает**. Кэш после подтверждения хранит серверную форму (без ключа), локальное состояние — клиентскую (с ключом).

**Чем это плохо:** `getChangedRecords` считает **все** сметы последней версии «изменёнными» при каждом `saveEstimates(все сметы)` → они снова ставятся в очередь → повторный аплоад без изменений → сервер поднимает `revision` каждой сметы → другие устройства гарантированно получают PT409-конфликты. Функциональность «ручного ретрая после конфликтов» (недавние коммиты) частично борется с симптомом, который порождает эта расyncхронизация форм.

**Доказательства:** Проверено: `estimateLifecycle.ts:45-47` — `parentId = item.id === latest.id ? undefined : latest.id; normalized.push({ ...item, parentId })`; `hashing.ts:6-8` — `Object.entries(...)` без фильтрации `undefined`; `JSON.stringify({a: undefined})` → `{}` (стандарт). e2e-тест этого не ловит — сценарий допускает счётчик «Локально: [1-9]\d*».

**Как исправить:** Единый `stableStringify`, игнорирующий ключи со значением `undefined` (одна строка в `hashing.ts`), либо нормализация записей перед сравнением хэшей. Заодно унифицировать второй хэш-стаблстрингифай в `indexedDbCache.ts:133-144` — их два, и это другой источник того же класса багов.

**Эффект:** Очередь перестаёт гонять неизменённые сметы; падает число ложных конфликтов PT409 и объём трафика синка.

**Риск изменения:** низкий (точечное изменение хэш-функции; есть тесты на стабильность кэш-ключей).

### Проблема 3. Вебхук оплаты отклоняет легитимные отложенные колбэки — деньги получены, подписка не выдана

**Приоритет:** P1

**Где обнаружена:** `api/webhook.ts:82-99, 158-166, 223`

**Что не так:** Replay-окно 300 секунд проверяется по `payload.payment_created_at ?? payload.created_at ?? payload.updated_at` — по времени **создания платежа**, а не события. Финальный статус `finished` у NowPayments приходит через минуты/часы после создания (ожидание подтверждений сети).

**Чем это плохо:** Отложенный колбэк отбрасывается со «Stale webhook payload», повторные доставки тоже (timestamp не меняется). Пользователь оплатил — премиум не активирован. Это прямая потеря выручки и тикеты поддержки.

**Доказательства:** Код `webhook.ts:82-99` — отсчёт от `payment_created_at`; продление на строке 223 при этом использует собственный захардкоженный срок 31 день.

**Как исправить:** Проверять окно по времени **события** (поле статуса/`updated_at` события), а не создания платежа; для статусов `finished`/`confirmed` — сверять с текущим состоянием подписки в БД и делать upsert идемпотентно (идемпотентность по `payment_id` уже есть — она спасает).

**Эффект:** Оплаченные подписки перестают теряться.

**Риск изменения:** низкий.

### Проблема 4. Лимиты всех тарифов отключены — UI продаёт то, чего нет

**Приоритет:** P1

**Где обнаружена:** `services/subscriptionConfig.ts:3-42`; контраст: `components/Subscriptions.tsx:15-58`

**Что не так:** Конфиги `free`, `basic` и `premium` **байт-в-байт идентичны** — все лимиты `null`, обе фичи `true`. При этом страница тарифов рекламирует «1 смета», «2 AI-запроса в день», «10 AI-запросов» и т.д. `getSubscriptionLabel` — заглушка, возвращающая «Безлимит» для любого тарифа.

**Чем это плохо:** Монетизация фактически выключена: любой зарегистрированный получает премиум-возможности (включая платные AI-запросы). При этом `App.tsx:312` на время загрузки подписки по умолчанию выдаёт `'premium'`. Похоже на временный откат для разработки, забытый в проде.

**Доказательства:** Проверено чтением `subscriptionConfig.ts` целиком (37 строк): три одинаковых объекта.

**Как исправить:** Решение на уровне владельца продукта: либо вернуть реальные лимиты в конфиг, либо убрать продающий лимиты UI. В любом случае — один источник правды и тест, ловящий расхождение рекламы и конфига.

**Эффект:** Соответствие продукта и монетизации; защита счёта AI-расходов.

**Риск изменения:** средний (влияет на поведение пользователей — требует продуктового решения).

### Проблема 5. Редактор смет: O(N×M) сканы каталога, двойное дерево таблицы и хэш всей сметы на каждое нажатие клавиши

**Приоритет:** P1

**Где обнаружена:** `components/EstimateEditor.tsx:1853, 2065` (сканы), `:1821` и `:2057` (двойное дерево), `:426-434` + `App.tsx:1365-1367` (хэш и зеркалирование черновика)

**Что не так:** Три наложенные проблемы в главном сценарии приложения:
1. На каждую позицию сметы при каждом рендере выполняется `works.some(w => normalizeKey(w.name) === normalizeKey(item.name))` и `checkMaterialPrice` (внутри — `materials.filter(...)` с нормализацией). При смете из 300 позиций и каталоге из 1000 записей — сотни тысяч вызовов `normalizeKey` на нажатие клавиши. Map-индекс уже существует (`:436-446`), но по «сырому» имени.
2. Десктопная таблица и мобильные карточки рендерятся **одновременно** (скрытие через CSS `hidden md:block` / `md:hidden`) — стоимость рендера позиций удваивается, включая п.1. Плюс ~400 строк дублирующегося JSX.
3. Каждый ввод символа вызывает `buildEstimateDirtySignature(estimate)` (хэш всего объекта сметы) и `onDraftChange` → App создаёт новый `editorDraft` → полный ре-рендер 2400-строчного App с пересозданием inline-обработчиков.

**Чем это плохо:** Плавность главного экрана деградирует с ростом сметы; на слабых машинах — ощутимый лаг ввода. Это не теоретическая проблема: скан выполняется в render-пути каждой строки.

**Доказательства:** Проверено чтением `EstimateEditor.tsx:1848-1870` — `.some(work => normalizeKey(work.name) === normalizeKey(item.name))` в теле `renderedSubItems.map`.

**Как исправить:** (1) Один `useMemo`-индекс `Map<normalizeKey(name), exists>` по каталогу на рендер сметы, а не на строку; (2) рендерить мобильную ветку по media-query-состоянию (`useMediaQuery`), а не обе всегда; (3) зеркалировать черновик в App только при открытии модалки сохранения, а dirty-подпись считать дебаунсно.

**Эффект:** Ввод в большой смете перестаёт упираться в CPU; минус ~400 строк дублированного JSX.

**Риск изменения:** средний (правки в render-пути; нужен ручной прогон редактора).

### Проблема 6. Логика «активна ли подписка» реализована 5 раз с расходящимся поведением

**Приоритет:** P1

**Где обнаружена:** `api/create-payment.ts:106-113`; `api/webhook.ts:223`; `api/expire-subscriptions.ts:46-56`; `services/subscriptionService.ts:18-46`; `components/Subscriptions.tsx:113-115`

**Что не так:** Пять независимых проверок статуса подписки: клиент с grace-периодом 1 час (`GRACE_MS`), сервер без grace, cron сбрасывает в `free` по своим порогам, в UI ещё одна сравнение дат. Константа «31 день» и цены продублированы (`create-payment.ts:35-49` vs `Subscriptions.tsx:15-58, 84-88`).

**Чем это плохо:** Клиент и сервер по-разному отвечают на вопрос «активен ли премиум» — расхождение проявится в пограничных случаях (истечение в момент оплаты, продление). Каждое изменение тарифов требует правки в 5 местах.

**Доказательства:** Сверка пяти фрагментов; grace есть только в `subscriptionService.ts`.

**Как исправить:** Один модуль `subscriptionState` (чистые функции: `isActive(sub, now)`, `tierExpiryDays`, цены) — импортируемый и в api-функциях, и на клиенте. Убрать в UI отображение цен, не связанных с `PRICE_BY_TIER`.

**Эффект:** Один источник правды по деньгам и срокам; правка тарифов в одном месте.

**Риск изменения:** низкий-средний.

### Проблема 7. «Похожая смета» — 5 реализаций с разными порогами

**Приоритет:** P1

**Где обнаружена:** `services/estimateIntelligence.ts:183-190, 436-437` (порог площади 0.2); `services/smartEstimateBuilder.ts:97-115` (0.3); `components/AIGenerationModal.tsx:132-182` (свой скоринг 50/30/20); `components/EstimateEditor.tsx:1155-1164` (инлайн-фильтр 0.3)

**Что не так:** Один и тот же доменный вопрос («какие прошлые сметы похожи на эту?») решается в 5 местах с разными порогами, критериями статусов/архива и фильтрацией версий. При этом в `estimateIntelligence.ts:79` уже есть правильный `filterToLatestEstimateVersions`, который используют Analytics и EstimateHistory, — редактор и модалка его игнорируют и дедуплицируют версии вручную (и без учёта даты при равных версиях).

**Чем это плохо:** AI-генерация, AI-анализ и детерминированный визард дают **разные** выборки «похожих» на одних данных — поведение системы несогласованно; любая правка правила требует правки в 5 местах, что уже не делается синхронно.

**Доказательства:** Сверка пяти фрагментов с координатами выше.

**Как исправить:** Единственная функция в `estimateIntelligence.ts` (`findSimilarEstimates(estimate, all, {areaTolerance})`) + `filterToLatestEstimateVersions`; компоненты вызывают её.

**Эффект:** Согласованное поведение всех AI-фич; −~100 строк.

**Риск изменения:** низкий (поведение каждого пути меняется предсказуемо, покрытие тестами сервиса уже есть).

### Проблема 8. Клиентские LLM-вызовы без таймаута; три разные политики retry; нет дедупликации дорогих AI-запросов

**Приоритет:** P1

**Где обнаружена:** `services/openRouterService.ts:651-661` (fetch без таймаута), `:641-701` (свой retry), `services/wikiAI.ts:128-172` (retry нет вообще, abort нет), `api/ai-chat.ts:174-213` (timeout 45 с, retry нет); `services/aiCache.ts` + `openRouterService.ts:1212-1218` (нет in-flight dedup)

**Что не так:** `fetch` получает только опциональный `signal` — если вызывающий не передал, запрос может висеть вечно (реальные вызовы `explainHouseCalculation` из HouseCalculator идут без signal). Общий примитив «вызов LLM с retry/timeout» отсутствует — три файла изобретают своё. При промахе кэша `generateEstimateWithAI` не публикует промис: два параллельных клика «Сгенерировать» = 8–12 платных LLM-вызовов вместо 4–6.

**Чем это плохо:** Зависший стрим = вечный спиннер для пользователя; клиентский retry поверх гейтвея с 45-секундным таймаутом даёт до ~3 минут ожидания без обратной связи; двойной прогон генерации — прямые деньги.

**Доказательства:** Координаты выше; grep по `event-stream|getReader` — стриминга нет нигде.

**Как исправить:** Один `callLLM(messages, {timeoutMs, retries, signal})`-примитив; дефолтный `AbortSignal.timeout(60_000)` на все клиентские вызовы; публикация in-flight промиса в `aiCache` по ключу генерации.

**Эффект:** Нет вечных спиннеров; экономия платных вызовов; одна точка настройки retry.

**Риск изменения:** низкий-средний.

### Проблема 9. Фича «AI-поиск цен» — пустая заглушка, прокинутая через 4 слоя UI

**Приоритет:** P1

**Где обнаружена:** `services/openRouterService.ts:1020-1028` (тело-заглушка); цепочка: `components/AIGenerationModal.tsx:564-571` → `components/EstimateEditor.tsx:1035-1052` → `services/geminiService.ts:21,45` → `openRouterService.ts:28, 1169, 1443-1450`

**Эффект:** Честный UI; −~95 строк мёртвого кода.

**Риск изменения:** низкий.

### Проблема 10. PDF-подсистема: два поколения одного документа, отключенная типизация, битая ссылка, сумма прописью без копеек

**Приоритет:** P1 (пачка связанных дефектов)

- В `pdfGenerator.ts:45` условие ссылается на несуществующую глобальную `LOGO_BASE64` — благодаря `@ts-nocheck` это ReferenceError, молча глотаемый try/catch при каждой странице. Там же ~29 строк мёртвой отрисовки шапки, которая сразу закрашивается (86-114 → drawPageDecor заливает страницу).

- Палитра/шапка/wordmark/форматирование денег скопированы из `premiumPdf` в `houseProposalPdf` и `houseProposalDocx` (~80 строк) мимо уже существующего `premiumPdfBrand.ts`.

**Доказательства:** Проверено чтением файлов; `pdfGenerator2.ts` — 27-строчный делегат (цитата в отчёте агента подтверждена).

**Как исправить:** Перенести уникальное поведение legacy `pdfGenerator` (если оно есть — сравнить выходы) и удалить файл; убрать `@ts-nocheck` из `pdfContractGenerator`, включая копейки в `numberToWordsRu` (сначала копейки словами, потом рубли); перевести `houseProposal*` на `premiumPdfBrand`.

**Эффект:** −~370 строк + устранение глотаемых ошибок типов; корректные договоры; jspdf уходит из главного бандла вместе с legacy-генератором.

**Риск изменения:** средний (визуальная сверка PDF до/после обязательна).

## 6. Архитектура и поддерживаемость

**Что мешает развиваться (по убыванию важности):**

1. **Файлы-монолиты держат главные сценарии.** App.tsx (2409 строк, 24 useState) — хаб, совмещающий роутинг, состояние всех таблиц, платёжную логику, offline-оркестрацию и сборку 5 контекстов. EstimateEditor (2486) и Analytics (2088) совмещают данные, вычисления и гигантский JSX. openRouterService (1806) — генерация, парсинг, retry, прайсинг, кэш-ключи в одном файле; `generateEstimateWithAI` — 324 строки с 6 уровнями вложенности, `analyzeMissingItems` — 253, `createPremiumEstimatePdf` — ~600 строк колбэка с ~20 замыканиями и мутацией внешнего `y`.

2. **Бизнес-логика протекает в UI.** Скоринг похожести и статистика истории — в AIGenerationModal; распределение скидки с пересчётом цен позиций — в `HouseCalculator.tsx:335-407` (`createDraft`); «latest version» дедупликация — вручную в EstimateEditor:990-1013 вместо существующего сервиса.

3. **Sync-состояние размазано по 6 каналам:** `useOfflineSync` (13 useState + 4 useRef), refs в App, SyncContext (по сути контекст тостов — имя вводит в заблуждение), подписка на offlineQueue, 2 window-события, `navigator.locks` + Map в offlineSync. Один факт «очередь изменилась» идёт тремя механизмами.

4. **`database.ts` (1138 строк) — половина не про базу:** `importData` — один оператор на ~295 строк с 5 почти одинаковыми merge-блоками и заведомо неверным подсчётом `inFileDuplicates` для смет (1115); блок export/transfer (635-791) просится наружу.

5. **`estimateIntelligence.ts` смешивает два домена:** AI-интелидженс (1-460) и управление дублями смет (462-665), не имеющее к AI отношения.

6. **EstimateContext слишком широкий** (view + все данные + черновики + raw-сеттеры): любое изменение `view`/`currentEstimate` перерендеривает всех подписчиков; raw-сеттеры используются компонентами в обход actions-слоя.

7. **Инфраструктурные ограничители:** `strict: false` (компилятор не ловит null-ошибки в платёжных хендлерах и синке); линт не покрывает api/electron/contexts; `package-lock.json` в `.gitignore` (невоспроизводимые сборки, CI на `npm install`); `xlsx` из CDN-URL без integrity; in-memory rate limiting в serverless.

**Циклических зависимостей не обнаружено.** Слой services не зависит от components; зависимости направлены App → contexts → components → services. Это сильная сторона.

## 7. Что уже реализовано хорошо и не нуждается в изменениях

1. **Offline-ядро** (outbox-first запись, идемпотентные RPC с `operation_id`, трёхстороннее слияние разделов, push-then-pull enforcement, карантин очереди, snapshot-проверки, rebase подтверждений). Это сложная область, и она спроектирована правильно — ломают её именно стыки (Проблемы 1-2), а не ядро.
2. **Тестовая культура сервисов:** 291 зелёный тест на самом рискованном чистом коде (CSV-парсер, слияние секций, очередь, цены, кэш-ключи, хэши), colocated с модулями, быстрый прогон 4.2 с.
3. **Разделение слоёв:** services → components направленность без циклов; тяжёлая математика (калькулятор дома, раскрой, план-факт) — вне UI и в тестах.
4. **AI-безопасность по контракту:** цены никогда не берутся из модели (только справочники), детерминистический фолбэк без AI, честные статусы `success/partial/unavailable/needs_clarification`, инвалидация кэша правками пользователя.
5. **Code splitting:** все тяжёлые представления через `React.lazy`, docx/PDF дома — динамические импорты, осознанное `runtimeCaching: []` в PWA.
6. **Supabase-слой:** батчинг, пагинация, честная верификация удаления при RLS-подавлении.
7. **Электрон-обвязка:** contextIsolation, блокировка will-navigate, single instance lock, ленивые импорты electron-store/updater; HMAC + timingSafeEqual + идемпотентность в вебхуке (структура верна — ломает её replay-окно).
8. **Отдельные образцовые модули:** `appUsage.ts` (полная очистка, teardown, защита от дозарядки времени), `useDebouncedSave.ts`, `duplicateManagement.ts` (fingerprint-сверка перед удалением), `cutting/importCsv.ts` (production-grade парсер с детекцией кодировки), `estimateSections.ts` (снапшот baseDocument с комментарием «почему»), `estimateActuals.ts` (чистые функции, единый roundMoney, null-семантика).

## 8. Какие оптимизации реально принесут пользу

1. **Индекс по нормализованному имени в редакторе** (Проблема 5) — единственная оптимизация, которая касается главного сценария каждый день.
2. **Удаление legacy `pdfGenerator.ts` + динамический импорт оставшихся** — минус ~350 КБ из критического пути первой загрузки (863 КБ → ~500 КБ).
3. **Устранение hash-churn** (Проблема 2) — минус холостой трафик синка и главный источник ложных PT409.
4. **In-flight dedup AI-генерации** — прямая экономия платных вызовов.
5. **Рендер одной ветки таблицы редактора** — минус ~50% работы рендера главного экрана.
6. **Дебаунс пересчёта калькулятора дома** — плавность слайдеров.
7. **Исправление replay-окна вебхука и проверка суммы** — защита выручки (не «перформанс», но эффект прямой).

Чего **не** делать сейчас: виртуализация таблицы редактора (пагинация/лимит 50 уже решают), `memo`/`useCallback` россыпью без профайлера, Redis/кэш-слой над Supabase (нагрузка не требует), переезд на стриминг AI (приятно, но не узкое место).

## 10. Краткий вердикт (по методике ponytail-audit)

**Verdict:** ядро (offline-синк, расчёты, тесты) — здоровое и взрослое; сначала чинить стыки: single-record диспатч синка (P0), hash-churn parentId, replay-окно вебхука, выключенные лимиты подписок. Потом — редактор (O(N×M) на нажатие) и дублирование бизнес-правил.

**Lean:** −~900 строк и −1 МБ артефактов возможно без потери поведения (мёртвый код ~400, legacy pdfGenerator 371, схлопывание копий ~150).

**Not checked:** фактическая схема индексов БД (миграции 6 таблиц в репозиторий не входят); e2e-прогон (требует сборки Electron); покрытие тестами в процентах (нет конфигурации); нагрузочное поведение Supabase при большом числе пользователей.
