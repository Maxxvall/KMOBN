# Аудит ИИ и план развития смет KMOBN

Дата: 21 сентября 2026 года. Статус: план, изменения продуктового кода не выполнены.

## Вывод

ИИ уже может помогать составлять черновик, искать пропуски и объяснять расчёт. Считать его ответы проверенной сметой сейчас нельзя: обнаружены воспроизводимые ошибки обработки результата, кэширования, отмены и проверки количеств. Они возникают независимо от качества выбранной модели.

Нужен управляемый процесс: структурированное задание → подбор проверенных данных → выбор состава работ → расчёт кодом → независимые проверки → объяснимый черновик → принятие пользователем. Более сильную модель следует выбирать по результатам испытаний этого процесса.

Фактический процент правильных ответов не измерен. Аудит проверяет код и синтетические сценарии; запросы к реальной модели, доступ к ключам, сохранённым пользовательским сметам и внешние публикации не выполнялись. Точность строительных нормативов и их актуальность этим аудитом не подтверждаются.

## Что работает сейчас

| Функция | Реализация | Оценка устройства |
| --- | --- | --- |
| Генерация сметы | `geminiService.ts` вызывает `openRouterService.ts`: структура → детализация разделов → самопроверка → коррекция количеств → цены | Полезная основа; много конфликтующих эвристик и недостаточно жёстких проверок |
| Поиск недостающих позиций | Локальные зависимости, ориентиры расхода, история и дополнение моделью | Хорошо, что часть проверки работает без модели; требуется контроль единиц и границ задания |
| Автодополнение | Справочники и вызов модели | Сначала стоит использовать локальный поиск; модель нужна для неоднозначных запросов |
| Пояснение калькулятора дома | Денежный расчёт выполняет код, модель получает сводку | Правильное разделение ответственности; текстовое объяснение всё равно нужно сверять с расчётом |
| «Умный» мастер | `smartEstimateBuilder.ts`: правила и статистика согласованных смет | Это отдельный алгоритм без вызова LLM; сейчас его правила отличаются от AI-генерации |
| Вопросы по базе знаний | `wikiAI.ts` | Отдельный сценарий поиска статей и ответа по контексту |
| «Обучение» | `aiLearning.ts`: пользовательские правки превращаются в подсказки | Это память и рекомендации для промпта, а не дообучение весов модели |

Все внешние сценарии используют общий `AI_CONFIG`. В коде есть модель по умолчанию, но фактическую конфигурацию окружения аудит не читал. Само имя `geminiService.ts` не означает, что используется Gemini.

Сохранить полезные решения: цены из справочников, выбранные разделы, эталонную смету, локальную проверку зависимостей, отказ доверять цене из ответа модели, независимый денежный расчёт калькулятора. Использовать существующие `WorkBundle`, `catalogWorkId`, `catalogMaterialId` и проверенные helpers вместо новой параллельной системы.

## Подтверждённые проблемы

### F01 — P1. Ответ модели может выполняться как JavaScript

`services/openRouterService.ts:457`, `:494`: после неудачного разбора JSON вызывается `new Function` на содержимом ответа. Синтетический ответ успешно установил безвредный маркер в изолированном контексте. Это подтверждает выполнение выражения; доступ к реальным данным и эксплуатация в установленном приложении не проверялись.

Исправление: только разбор данных и проверка схемы; невалидный ответ отклонять. Вредоносные инструкции могут попадать и в описание проекта, и в полученный контекст, поэтому одного запрета в промпте недостаточно.

### F02 — P1. Изменённое задание может получить старую смету

`services/openRouterService.ts:1459`: ключ кэша генерации не содержит описание, количество окон/дверей, содержимое и цены справочников, версии промпта/модели/истории. При повторном запросе с новым описанием, числом окон и ценой 999 вместо 100 не было ни одного нового обращения к mock API; вернулась цена 100.

Аналогичные пробелы есть у анализа (`:1963`, нет количеств, единиц и разрешённых категорий) и автодополнения (`:1758`, нет содержимого справочников и текущих позиций). Кэш готовой сметы особенно опасен, потому что возвращает уже назначенные цены.

Исправление: общий построитель ключа по нормализованному полному входу, пользователю, версиям данных/правил/модели. Цены при применении повторно разрешать по актуальному справочнику. Не продлевать абсолютную свежесть результата каждым чтением.

### F03 — P1. Проверки количества сами искажают результат

`services/openRouterService.ts:272`, `:950`, `:919`, `:215`: несколько последовательных коррекций используют разные предположения. `sanitizeQuantities` превратил 500 шт. крепежа в 50 при площади 100 м². Расчёт упаковок сначала использует площадь поверхности раздела, затем следующая функция может заменить её расчётом от площади пола.

`services/constructionNorms.ts`, функция `checkNormAnomalies`: сравниваются числа без приведения единиц. Восемь упаковок мембраны по 25 м² получили предупреждение о недостатке относительно 81–270 м², хотя 8 × 25 = 200 м².

`services/openRouterService.ts:163`, `:1228`: регулярные выражения с `\b` некорректно распознают часть русских слов и обозначений. В отдельной проверке «Окно стандарт» и «Саморезы кровельные» не распознаны соответствующими классификаторами, а площадь упаковки «Утеплитель 3 м²» не извлечена.

Исправление: явные единицы, фасовка и назначение в справочнике; единый расчёт покрытия и закупки; аномалия должна выдавать объяснение, а не молча заменять число.

### F04 — P1. Отмена генерации не гарантирует остановку

`services/openRouterService.ts:1627`, `:1655`, `:1662`: отмена ловится как обычная ошибка и приводит к резервной генерации из каталога. Проверка с уже отменённым `AbortSignal` вернула позиции вместо отклонения операции.

`components/EstimateEditor.tsx:980`, `:1016`: перед применением результата нет проверки, что именно этот запрос ещё актуален и не отменён. Текущие позиции редактора заменяются объединением шаблона и результата генерации.

Исправление: передавать отмену наверх без fallback; проверять request ID и ревизию сметы; показывать изменения до применения. Отмена, новый запрос и ручное редактирование во время ожидания не должны менять смету старым ответом.

### F05 — P1. Ограничения задания остаются пожеланием в промпте

`services/openRouterService.ts:1605`, `:1688`: финальная самопроверка не получает полный справочник и явный список выбранных разделов; после ответа нет общего фильтра результата по разрешённому scope. Синтетическая генерация при выбранной только кровле вернула электрику.

`services/openRouterService.ts:1250`: резервная генерация перебирает все позиции выбранных разделов. Описание исключений в неё не передаётся; альтернативные виды материалов могут попасть одновременно. `services/geminiService.ts:105` дополнительно содержит переход на демонстрационные позиции с фиксированными ценами при исключении из основного сервиса; UI блокирует запуск без ключа, но эта ветка обработки ошибок остаётся.

Исправление: формализовать включения/исключения, технологию и ответственность за материалы; проверять ограничения после каждого этапа и после fallback. Резервный результат помечать отдельным режимом, не подставлять демонстрационные сметы.

### F06 — P1. История и оценка качества создают ложную уверенность

`services/estimateIntelligence.ts:187`, `:429` требуют совпадения региона, но `Estimate` в `types.ts:98` региона не содержит. Генерация передаёт непустой регион. В проверке подходящая по типу и площади смета без такого поля дала `similarCount = 0`.

`services/openRouterService.ts:528` объявляет исторические сметы «финальными, проверенными», хотя `filterToLatestEstimateVersions` выбирает последние неархивные версии без фильтра согласования и проверки полноты. `scoreEstimateQuality` оценивает пустой список на 0.8475 из 1; это математический результат текущей формулы, а не оценка точности ИИ. Такие признаки не обосновывают слово «эталон».

Исправление: явный статус допуска в обучающую выборку; дедупликация версий; обязательные метаданные региона, технологии и объёма работ; неизвестный регион не считать ни совпадением, ни доказанным противоречием. Отдельно измерять полноту, корректность количества, актуальность цен и покрытие источниками. Пустая смета не проходит проверку качества.

### F07 — P1. Ключ внешнего ИИ используется клиентом

`services/aiConfig.ts:25`, `:47` читает `VITE_OPENROUTER_API_KEY`, а `openRouterService.ts:744` формирует Authorization в клиентском сервисе. Если общий ключ передан при сборке, эта архитектура включает его в клиентский код. Наличие реального ключа в опубликованной сборке не проверялось.

Vite прямо документирует раскрытие `VITE_*` клиенту: [Env Variables and Modes](https://vite.dev/guide/env-and-mode).

Исправление: серверный AI endpoint с авторизацией, проверкой принадлежности данных, ограничением запросов и бюджетом. Перенос общего ключа только в Electron main не защищает его от владельца распространяемого приложения. При подтверждении прежней публикации ключа запланировать ротацию после изменения архитектуры.

### F08 — P2. Калькулятор и мастер используют неодинаковую логику

`components/HouseCalculator.tsx:197`: после обновления истории вычисляется `reviewedResult`, но сводка модели далее собирается из старого `result`. Модель может объяснять прежнюю сумму, пока интерфейс уже показывает новую. В основном сценарии ошибка необязательного AI-пояснения попадает в общий catch и очищает вычисленный результат (`:178`).

`services/smartEstimateBuilder.ts:97`: при недостатке похожих примеров используется вся согласованная история, что может смешивать типы объектов. `openRouterService.ts:603` принудительно считает все работы одной услугой, тогда как мастер использует и м², и погонные метры. В `Work` нет явной единицы тарифа: корректность цены за услугу нельзя проверить автоматически.

Исправление: единый контракт расчёта и источников, согласованные единицы, сводка по актуальному снимку. Сбой пояснения не должен уничтожать готовый денежный расчёт.

### F09 — P2. Память обобщает правки без достаточного контекста

`services/aiLearning.ts:37`, `:39`: единое локальное хранилище не разделено по пользователю; подпись контекста не включает scope, хотя описание передаётся. Удаление материалов в заказе «только работы» может дать подсказку об их удалении для полного заказа того же типа.

`services/aiLearning.ts:142` считает отношение количеств, не учитывая смену единицы. Перевод 100 м² в 4 упаковки будет принят за уменьшение количества, с ограничением множителя до 0.2. `components/EstimateEditor.tsx:1340` записывает исправления при сохранении, но не обновляет baseline и не содержит ID события: повторное сохранение той же правки может увеличить её вес.

Исправление: изоляция по пользователю, точный scope, catalog ID, базовые единицы, причина изменения, идемпотентный ID события и допуск подтверждённых примеров. Это наблюдения по коду; работа с реальным localStorage не выполнялась.

### F10 — P2. Wiki может пропустить нужную статью и показать непроверенный источник

`services/wikiAI.ts:59` индексирует заголовок, теги и только первые две строки статьи. Важные сведения в середине текста не участвуют в поиске. При отсутствии совпадений запрос к модели всё равно выполняется; при отсутствии значимых токенов выбираются первые пять статей.

`services/wikiAI.ts:111`, `:143`: правила, статьи и вопрос объединены в одно пользовательское сообщение, результат возвращается свободным текстом. `components/Wiki/WikiAIChat.tsx:72` выводит название источника даже при отсутствии такой статьи. Это не доказательство фактических галлюцинаций модели, но приложение их не отсекает. В `askWikiAI` передаётся только текущий вопрос: уточнения со ссылкой на предыдущий ответ не имеют истории диалога.

Исправление: поиск по фрагментам всей статьи, порог достаточности найденных данных, отдельные инструкции и контекст, структурированные source IDs с проверкой принадлежности найденным фрагментам. Для последовательных уточнений — ограниченная история диалога; иначе явно обозначить независимый формат вопросов.

## Целевой пользовательский сценарий

1. Пользователь описывает объект: например, «ремонт кровли 80 м², металлочерепица, материалы заказчика, демонтаж включить».
2. ИИ показывает понятую задачу: ремонт; площадь именно кровли; выбранная технология; только работы и демонтаж; материалы не покупать. Запрашивает только сведения, без которых выбранный метод расчёта невозможен.
3. Приложение находит подходящие работы и комплекты по ID. Если работа не найдена, показывает пробел справочника, а не подменяет её похожей по одному слову.
4. Код рассчитывает объёмы, фасовку, округление, цены и сумму. Неизвестное остаётся неизвестным; приближения явно обозначаются.
5. Проверки выявляют нарушения scope, несовместимые материалы, пропуски, дубли и устаревшие цены. ИИ объясняет обнаруженное и предлагает уточнения.
6. Пользователь видит черновик и изменения: что добавится/удалится, какие допущения приняты, какие позиции требуют решения. Применение атомарно и допускает откат.
7. Принятые исправления сохраняются с причиной. «Ошибка количества», «изменилось задание» и «материалы заказчика» имеют разное значение для будущих рекомендаций.

Для каждой позиции хранить краткое проверяемое обоснование: источник каталога, формула, входные величины, коэффициент отходов, единица цены, дата цены и использованное допущение. Внутренние рассуждения модели для этого не нужны.

## План внедрения

### Этап 1. Стабилизировать существующие сценарии

Первый пакет: F01–F05 и ошибки UI из F08. Удалить исполнение ответов, демонстрационные fallback, исправить отмену и кэш, запретить выход за scope, отключить неподтверждённые автоматические коррекции объёмов. Сохранить локальный расчёт при сбое пояснений. На найденные случаи добавить focused regression tests.

Ввести состояния `success`, `needs_clarification`, `partial`, `unavailable`, `cancelled`, а также источник результата `model`/`rules`/`template`. Пустой или частичный ответ не маскировать успешной генерацией. Unknown price — отдельное состояние, не бесплатная позиция в окончательной сумме.

Критерий готовности: все сценарии F01–F05 воспроизводимо закрыты; отменённый/устаревший ответ не меняет редактор; плохой ответ не превращается в правдоподобную готовую смету.

### Этап 2. Защитить общий доступ к моделям

Сделать общий серверный AI gateway для веба и Electron. Авторизация, границы пользователя/организации, лимиты, timeout на запрос и на задачу, ограниченная параллельность разделов, retry только для временных ошибок, учёт Retry-After, модель резервирования с теми же требованиями к данным. Отмена в клиенте не всегда останавливает уже оплаченный inference у провайдера — учитывать фактическую семантику API.

Отправлять минимально необходимую выдержку без клиентских реквизитов. Сырые промпты и ответы не писать в production-логи; текущие preview/full-response логи заменить техническими метриками. Политику хранения провайдеров настроить явно и проверить доступность соответствующих маршрутов. OpenRouter описывает управление параметрами провайдеров в [Provider Selection](https://openrouter.ai/docs/guides/routing/provider-selection).

Критерий готовности: общего API-секрета нет в клиентской сборке; один пользователь не может читать контекст другого; превышение бюджета завершается понятной ошибкой; журнал содержит метрики, а не содержимое смет.

### Этап 3. Создать общий расчётный контракт

Добавить версионируемый `ProjectSpec`: режим работ, технология, регион, площадь и её смысл, габариты/периметр при необходимости, этажность, высоты, крыша, проёмы, включённые/исключённые разделы, материалы заказчика, допущения и неизвестные параметры. Не заставлять заполнять все поля для каждой задачи.

Расширить справочники: `unit`, `priceUnit`, фасовка, полезная площадь/объём, размеры, назначение, совместимость, единица тарифа работ и дата цены. Сначала использовать существующие IDs и `WorkBundle`; добавить к комплектам условия применимости и базы масштабирования. Старые записи мигрировать без угадывания единиц: неподтверждённые поля отмечать для проверки.

Один расчётный модуль для генератора, мастера и анализа. Разделять физический объём и закупочное количество; запас, нахлёсты и округления задавать правилами конкретного материала. Геометрический расчёт по известным размерам имеет приоритет над статистическим приближением. При недостатке геометрии — запрос данных либо диапазон с допущением.

Критерий готовности: одинаковый вход даёт одинаковые объёмы во всех режимах; единицы совместимы; каждая цена имеет базовую единицу; каждое изменение количества объясняется формулой. Отдельные проверки для частичного ремонта, нескольких слоёв, упаковок, листов, погонных метров, крепежа и работ по тарифу.

### Этап 4. Улучшить понимание и подбор контекста

Модель сначала извлекает `ProjectSpec`, выявляет противоречия и возвращает `missingFields`; только затем выбирает состав. Числовые параметры формы имеют приоритет над догадками. При конфликте описания и формы уточнить конкретное противоречие.

Выбирать справочник и историю по технологии, назначению, единицам, scope и допуску качества, затем ранжировать по сходству. Не брать просто первые строки каталога и не объявлять всю историю эталонной. Восстановить работу региона; отделить согласование с заказчиком от инженерной проверки. Для неизвестного региона предусмотреть явно обозначенное расширение поиска.

Ответ модели содержит ID разрешённых позиций, назначение и необходимые исходные величины. Схему передавать через `response_format: json_schema` для совместимых endpoint, на своей стороне всегда валидировать структуру и бизнес-правила. Поддержка strict зависит от endpoint; JSON Schema сама по себе не доказывает правильность расчёта: [OpenRouter Structured Outputs](https://openrouter.ai/docs/guides/features/structured-outputs).

Сначала улучшить текстовый поиск с фильтрами и синонимами; семантический индекс добавлять, если на контрольных вопросах сохраняется заметный недостаток найденных релевантных данных. Источники передавать как данные, а не как инструкции.

Критерий готовности: исключения «без электрики», «только работы», «материалы заказчика», нестандартные размеры, ноль проёмов и изменения задания соблюдаются; неоднозначный материал не выбирается молча; все принятые catalog IDs существуют.

### Этап 5. Сделать проверку и знания доказательными

Проверяющий модуль получает тот же `ProjectSpec`, актуальные справочники, вычисленные объёмы, источники и результаты правил. Он возвращает список замечаний и предложений к конкретным позициям. Повторная генерация всей сметы той же моделью не считается независимой проверкой.

Разделить проверки: комплектность по проверенным комплектам; количества/единицы кодом; актуальность цен по справочнику; смысловые противоречия моделью. Правила применимости нормативов выбирать по технологии и виду работ; ссылка на документ не должна добавляться как признак качества без проверенного основания.

Для Wiki: ответ по релевантным фрагментам с идентификаторами источников и проверяемыми ссылками; при отсутствии основания — понятный отказ и уточнение. Хранить версию, область применения и дату проверки источника. Строительные рекомендации и численные нормативы допускать после проверки профильным специалистом по первоисточнику.

Критерий готовности: у каждого нормативного утверждения есть подходящий фрагмент источника; выдуманный ID отклоняется; нет универсального применения одного документа ко всем объектам; отсутствие данных не превращается в уверенный совет.

### Этап 6. Настроить память и выбрать модели по измерениям

Сохранять feedback с пользователем, проектом, ревизией, областью работ, причиной правки, базовой единицей и версией правил. Удаление позиции из сметы с материалами заказчика не означает, что её всегда надо удалять. Повторное сохранение одной правки не должно усиливать её вес. Смена единицы не является простым множителем количества.

Использовать память сначала как проверяемые рекомендации. Новое общее правило допускается после нескольких независимых подтверждений и проверки на отложенных примерах; спорные правила можно отключить и откатить. Дообучение весов рассматривать после накопления качественного размеченного набора и доказанного преимущества над подбором контекста.

Сравнить текущую конфигурацию и 2–3 доступные модели на одном наборе заданий. Выбрать модель отдельно для извлечения задания, подбора/проверки состава и Wiki. Простое автодополнение оставить локальному поиску; сильную модель вызывать для сложных случаев и смысловой проверки. Бесплатность или известность модели не заменяет оценку качества; стоимость измерять на принятую смету с учётом повторов и исправлений.

Критерий готовности: выбранная конфигурация улучшает качество на отложенной выборке и укладывается в согласованный бюджет; версия модели/промпта фиксируется; регрессия позволяет вернуться к предыдущей конфигурации.

## Как измерять результат

Начать с 30–50 обезличенных заданий, проверенных сметчиком, и расширять набор по реальным ошибкам. Разделять данные для настройки и итоговой оценки по проектам, а не по версиям одной сметы. Текущие ошибочные результаты не использовать как эталон. Каждую stochastic-конфигурацию проверять несколькими прогонами, указывать размер выборки и разброс.

Предлагаемые стартовые критерии ниже — требования для будущего выпуска, а не уже достигнутые показатели.

| Проверка | Критерий |
| --- | --- |
| Выполнение содержимого ответа | 0 случаев |
| Выход за явно заданный scope | 0 принятых позиций в контрольных сценариях |
| Отмена, устаревший запрос, другой пользователь | 0 несанкционированных применений/смешений |
| Schema и catalog IDs | 100% принятых результатов проходят локальную проверку |
| Арифметика и преобразование единиц | 100% контрольных детерминированных примеров; допуск только на заранее заданное округление |
| Полнота критических позиций | Предварительная цель ≥95% на размеченных задачах; список обязательного определяет сметчик |
| Точность предлагаемых позиций | Предварительная цель ≥95%; исключать конфликтующие альтернативы |
| Количества | Допуск задаётся по материалу, методу и полноте исходных данных; единого обещания «±5%» для всех смет нет |
| Нормативные ссылки | 100% разрешаются в источник; соответствие утверждению проверяется отдельно |
| Отсутствующие данные | Система уточняет или показывает ограничение, а не выдумывает |
| Ручная доработка | Снижение доли изменённых/удалённых позиций относительно измеренного baseline |
| Скорость и стоимость | p50/p95 времени и стоимость принятой сметы; численные лимиты определить после baseline и бюджета |

Обязательные сценарии: небольшой ремонт; только работы; материалы заказчика; кровля без стен; 0/несколько проёмов; прямоугольный и двухэтажный объект; разные толщины утепления; одинаковые названия с разными размерами; материал в упаковках; 500 единиц крепежа; пустой каталог; устаревшие цены; черновик в истории; отсутствующий регион; смена scope; отмена; 429/timeout; обрезанный JSON; вредоносная инструкция в описании/статье; вопрос без ответа в Wiki.
