### Реализовано

- F1: обычные записи и удаления используют RPC с `expected_revision` и `operation_id`; конфликт остаётся в очереди и не затирает серверную версию.
- F2–F3: база разделов фиксируется до первой мутации, подтверждённая ревизия применяется в локальный кэш, а более новая локальная правка перебазируется.
- F4–F5: локальный владелец берётся из remembered workspace, `anon` запрещён, операции имеют UUID, а синхронизация вкладок защищена Web Locks.
- F6–F7: Supabase API исключён из PWA runtime-кэша; полная очистка удаляет кэш и outbox после закрытия соединений и предупреждает о pending-изменениях.
- F8–F9: зарплатный autosave ждёт актуальную загрузку, черновики раскроя и комнаты разделены по пользователям.
- F10–F12: постоянные ошибки не блокируют независимые операции, проверка обновлений Electron дожидается результата, а статус офлайна учитывает готовность Service Worker/оболочки.
- Дополнительно: экспорт использует единый `exportData()` и включает сметы, каталоги, зарплаты и разделы; добавлены regression/unit/E2E проверки.

## 1. Подтверждённые проблемы

P1 — устранить в первую очередь из-за риска для данных или основного сценария. P2 — важное ограничение надёжности/интерфейса. «Воспроизведено» ниже означает изолированную проверку на синтетических данных, а не работу с реальными пользовательскими данными.

### F1. P1 — обычные записи синхронизируются без проверки конкурентных изменений

Платформы: сайт и ПК.

Основание: [services/offlineSync.ts:97](C:/Users/Mexxvell/Desktop/Боты/СметыKMOBN/services/offlineSync.ts:97), [services/supabase.ts:110](C:/Users/Mexxvell/Desktop/Боты/СметыKMOBN/services/supabase.ts:110). В отличие от разделов, обычные сметы, материалы, работы, комплекты, шаблоны и зарплатные расчёты отправляются полным payload через upsert без ожидаемой серверной ревизии.

Сценарий: ПК офлайн меняет старую смету, сайт онлайн меняет ту же запись. После подключения ПК отправляет свой payload поверх версии сайта. Удалённая на другом устройстве запись также может появиться снова после upsert устаревшей локальной копии. Собственная история версий сметы не заменяет проверку конкурентной записи одного ID.

Доказательство: путь записи проверен по коду. Серверные триггеры и политики развёрнутой базы вне репозитория не проверялись.

Исправление: серверная ревизия и условная запись/удаление; при несовпадении сохранять обе версии и показывать выбор. Автоматически объединять только доказуемо независимые поля. Для удаления нужна политика конфликтов и сохранение информации об удалении.

Приёмка: изменение одного ID на двух устройствах не теряет ни одну версию; сочетания update/update и delete/update дают понятный результат.

### F6. P1 — кэш API в PWA может откатывать актуальные локальные данные

Платформа: только сайт.

Основание: [vite.config.ts:39](C:/Users/Mexxvell/Desktop/Боты/СметыKMOBN/vite.config.ts:39), [services/database.ts:248](C:/Users/Mexxvell/Desktop/Боты/СметыKMOBN/services/database.ts:248), [services/database.ts:285](C:/Users/Mexxvell/Desktop/Боты/СметыKMOBN/services/database.ts:285), [services/indexedDbCache.ts:313](C:/Users/Mexxvell/Desktop/Боты/СметыKMOBN/services/indexedDbCache.ts:313).

Для всех Supabase GET настроен NetworkFirst с кэшем на сутки. При сетевой ошибке он возвращает сохранённый ответ как обычный успешный Response. Это штатная семантика [Workbox NetworkFirst](https://developer.chrome.com/docs/workbox/modules/workbox-strategies/#network-first-network-falling-back-to-cache). Код базы принимает такой ответ за полный актуальный серверный снимок и обновляет IndexedDB.

Сценарий по коду: GET сохранил старую версию; изменение/удаление успешно отправлено и снято с очереди; сеть пропала до следующего успешного GET. Фоновое чтение может получить старый API-кэш и откатить локальную запись или вернуть удалённую. В database.ts фоновое чтение не запрещено при navigator.onLine=false. Полноценный браузерный сценарий пока не запускался.

Исправление: исключить Auth и пользовательские REST/RPC API из непрозрачного Service Worker fallback; оставить управляемую офлайн-логику IndexedDB/outbox. Для публичных статических ресурсов задавать отдельные точные правила. При обновлении удалить прежний supabase-api cache.

Приёмка: успешная запись/удаление → отказ GET → reload не возвращают старые данные. При сбое Auth нельзя принимать кэшированный ответ за свежую проверку пользователя.

### F12. P2 — «Офлайн готово» не подтверждает готовность самого сайта

Платформа: сайт.

Основание: [hooks/useOfflineSync.ts:42](C:/Users/Mexxvell/Desktop/Боты/СметыKMOBN/hooks/useOfflineSync.ts:42), [services/indexedDbCache.ts:181](C:/Users/Mexxvell/Desktop/Боты/СметыKMOBN/services/indexedDbCache.ts:181), [components/StatusIndicators.tsx:45](C:/Users/Mexxvell/Desktop/Боты/СметыKMOBN/components/StatusIndicators.tsx:45).

Готовность определяется наличием семи полных снимков IndexedDB. Регистрация/активация Service Worker и готовность оболочки не учитываются. При полном кэше данных и отсутствующем SW интерфейс может обещать офлайн, хотя полная перезагрузка без сети не откроет сайт.

Исправление: отдельно показывать готовность данных, готовность приложения и состояние отправки. Для Electron готовность оболочки определяется локальными ресурсами установленного приложения, а не SW.

Приёмка: ошибка/отсутствие SW не даёт зелёный статус полного офлайна; после успешной подготовки сайт открывается по URL после закрытия браузера без сети.

## 2. Что уже сделано правильно

- Семь основных коллекций хранятся в IndexedDB по пользователю; очередь также разделена по userId.
- Изменение сначала попадает в outbox, затем в кэш; чтение накладывает pending-изменения поверх сохранённого снимка.
- Последовательные операции над записью сворачиваются; удаление остаётся в очереди до подтверждения.
- В одном JS-контексте старое подтверждение не удаляет новую операцию с отличающимся sequence.
- Есть повторные попытки с задержкой, сохранение сведений об ошибке и карантин старой очереди.
- Подготовка рабочего пространства отправляет локальные изменения перед загрузкой облачных снимков.
- Фоновые обновления защищены от локальных мутаций в том же контексте; полные снимки учитывают удалённые записи и пустые таблицы.
- Загрузка таблиц постраничная; лимиты интерфейса не должны обрезать полный офлайн-снимок.
- Electron грузит локальный dist через loadFile; PWA в Electron отключён корректно.
- Web precache glob включает JS/CSS, PNG и TTF: ленивые экраны и имеющиеся локальные шрифты PDF по конфигурации покрыты. Содержимое реальной production-сборки в этом аудите не проверялось.

Эти решения нужно сохранить и дополнить, а не переписывать всё офлайн-хранилище.
